== Diagrama de despliegue

ifdef::arc42help[]
[role="arc42help"]
****
.Content
The deployment view describes:

 1. technical infrastructure used to execute your system, with infrastructure elements like geographical locations, environments, computers, processors, channels and net topologies as well as other infrastructure elements and

2. mapping of (software) building blocks to that infrastructure elements.

Often systems are executed in different environments, e.g. development environment, test environment, production environment. In such cases you should document all relevant environments.

Especially document a deployment view if your software is executed as distributed system with more than one computer, processor, server or container or when you design and construct your own hardware processors and chips.

From a software perspective it is sufficient to capture only those elements of an infrastructure that are needed to show a deployment of your building blocks. Hardware architects can go beyond that and describe an infrastructure to any level of detail they need to capture.

.Motivation
Software does not run without hardware.
This underlying infrastructure can and will influence a system and/or some
cross-cutting concepts. Therefore, there is a need to know the infrastructure.

.Form

Maybe a highest level deployment diagram is already contained in section 3.2. as
technical context with your own infrastructure as ONE black box. In this section one can
zoom into this black box using additional deployment diagrams:

* UML offers deployment diagrams to express that view. Use it, probably with nested diagrams,
when your infrastructure is more complex.
* When your (hardware) stakeholders prefer other kinds of diagrams rather than a deployment diagram, let them use any kind that is able to show nodes and channels of the infrastructure.


.Further Information

See https://docs.arc42.org/section-7/[Deployment View] in the arc42 documentation.

****
endif::arc42help[]

=== Nivel de infraestructura 1

ifdef::arc42help[]
[role="arc42help"]
****
Describe (usually in a combination of diagrams, tables, and text):

* distribution of a system to multiple locations, environments, computers, processors, .., as well as physical connections between them
* important justifications or motivations for this deployment structure
* quality and/or performance features of this infrastructure
* mapping of software artifacts to elements of this infrastructure

For multiple environments or alternative deployments please copy and adapt this section of arc42 for all relevant environments.

Motivation::

La aplicación se despliega sobre un servidor de Azure, en el que cada módulo que constituye el sistema se encuentra encapsulado en un contenedor de Docker. El usuario interactua con el sistema a través de una interfaz diseñada con React. Está se comunica con el back-end mediante OpenApi. A su vez, el back-end se comunica con la base de datos con la api mencionada anteriormente.
El front-end también se comunica con el módulo de juego mediante los módulo Bot-server y Game-server.

Características de calidad/rendimiento::

El hecho de emplear Docker para encapsular cada uno de los módulos del sistema en distintos contenedores permite que el sistema sea escalable y portable. Además, la separación de las distintas partes en distintos contenedores
facilita el mantenimiento y la extensibilidad. Además,  aumenta el rendimiento en comparación con emplear un contendor aislado, ya que se permite aislar las dependencias de cada módulo. Por otro lado, el uso de Docker permite el despliegue
continuo de nuestra aplicación.

Mapeo de los bloques de construcción a infraestructura::

[cols="1,2" options="header"]
|===

| **Nombre** | **Descripción**

| Azure | Servicio con el servidor en el que se encuentra la aplicación.

| Docker | Genera cada uno de los contenedores para almacenar cada uno de los módulos de la aplicación.

| WebApp | Front-end diseñado con React para la interacción con el usuario.

| Users | Back-end diseñado con Node para gestionar la interacción con la BD. 

| Gamey | Módulo Rust con la lógica del juego y del bot.

| Database | Almacena un registro de los usuarios de la aplicación, las partidas realizadas, los usuarios obtenidos, ...

|===

=== Nivel de infraestructura 2

En este nivel se detalla la estructura interna de los elementos de infraestructura definidos en el nivel 1. En particular, se descompone el nodo Azure VM y el entorno Docker para mostrar cómo se organizan los contenedores, servicios auxiliares y la persistencia de datos.

[plantuml,"Nivel de infraestructura 2",png]
----
@startuml
skinparam monochrome true
left to right direction

node "Azure VM\n(Linux Ubuntu 24.04)" as VM {
  node "Docker" as Docker {

    node "webapp\n(React + Vite)" as WebApp
    node "users\n(Node.js)" as Users
    node "gamey\n(Rust)" as Gamey
    database "MySQL" as Database

    node "Monitoring" as Monitoring {
      node "Prometheus" as Prometheus
      node "Grafana" as Grafana
    }
  }
}

actor Navegador

Navegador <--> WebApp : HTTPS / UI
WebApp <--> Users : HTTP/JSON
WebApp <--> Gamey : HTTP/JSON

Users <--> Database : SQL
Users <--> Prometheus : Métricas
Grafana <--> Prometheus : Consultas de métricas

@enduml
----

Motivación::

El sistema se sostiene en una máquina virtual Ubuntu 24.04 en Azure sobre la que se despliega Docker, porque esto simplifica la ejecución aislada de cada servicio y permite reproducir el entorno de forma consistente en despliegues de prueba, integración y producción.
Los módulos webapp, users y gamey se publican como imágenes independientes, mientras que MySQL actúa como base de datos persistente y Prometheus/Grafana proporcionan la observabilidad del sistema.

El flujo de despliegue confirma además que cada release pasa por pruebas de Node, Rust y E2E antes de publicar imágenes y actualizar el sistema. Esto refuerza una estrategia de despliegue continua, basada en contenedores y con separación clara entre construcción, publicación y ejecución.

Características de calidad/rendimiento::

El uso de contenedores independientes mejora la portabilidad y reduce el acoplamiento entre servicios, porque cada bloque se ejecuta con sus dependencias y configuración propias.
La base de datos MySQL queda aislada como servicio persistente, lo que facilita las tareas de mantenimiento y recuperación sin afectar al resto de componentes.

La presencia de Prometheus y Grafana añade observabilidad al entorno, permitiendo monitorizar el comportamiento de la aplicación y detectar incidencias de forma más rápida.
Además, el despliegue automático desde GitHub Actions favorece tiempos de entrega cortos y una actualización uniforme de los servicios desplegados.

Mapeo de los bloques de construcción a infraestructura::

[cols="1,2,2" options="header"]

|===

| Elemento de infraestructura | Rol | Responsabilidad

| Azure VM | Host físico/virtual con Ubuntu 24.04 | Ejecuta toda la infraestructura mediante Docker.

| Docker | Motor de contenedores y Docker Compose | Aísla y orquesta los servicios de la solución.

| webapp | Imagen Docker del front-end React/Vite | Sirve la interfaz de usuario y consume las APIs del sistema.

| users | Imagen Docker del backend Node.js | Gestiona autenticación, lógica de usuarios y acceso a datos.

| gamey | Imagen Docker del motor Rust | Valida jugadas, gestiona la lógica del juego y la interacción con bots.

| MySQL | Contenedor de base de datos | Persiste usuarios, partidas, puntuaciones y otros datos del sistema.

| Prometheus | Contenedor de monitorización | Recoge métricas del backend y del entorno de ejecución.

| Grafana | Contenedor de visualización | Presenta paneles y cuadros de mando a partir de las métricas de Prometheus.

|===
